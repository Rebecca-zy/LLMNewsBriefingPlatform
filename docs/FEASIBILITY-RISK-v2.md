# AI热点推送系统 - 可行性与风险分析（V3）

## 1. 可行性结论
结论：可行性高。现有 demo 已具备抓取、生成、展示和推送能力，当前重点是稳定性与运维规范化。

## 2. 当前技术实现（已落地）
1. 抓取与生成：RSS 抓取、去重、摘要、领域推断、Markdown/JSON 输出。
2. 前端展示：对客详情页样式（浅色科技风），含日期切换和热点条目卡。
3. 推送能力：企业微信群机器人 webhook 推送，支持内容长度控制与 webhook 归一化。
4. 兼容策略：历史旧数据（含评分文案）在前端渲染时会自动转换为新样式语义。

## 3. 风险点与应对
### 3.1 数据源风险
风险：RSS 404、结构变化、响应超时。
应对：
1. 移除失效源（如 Anthropic 404 源）。
2. 多源冗余与单源失败隔离。
3. 失败日志保留，避免阻断整体生成。

### 3.2 推送风险
风险：
1. 40058（markdown 超长）。
2. 93000（webhook 非法）。
应对：
1. 推送前自动截断与条目数限制。
2. webhook 归一化（支持 key / URL / webhook=URL）。
3. 清晰错误信息提示与 curl 验证模板。

### 3.3 内容质量风险
风险：翻译质量波动、领域推断偏差。
应对：
1. 规则词典持续迭代。
2. 保留原文链接与免责声明。
3. 支持后续加入人工复核环节。

### 3.4 UI 可用性风险
风险：字号过大、密度失衡、移动端排版溢出。
应对：
1. 统一字号/间距尺度。
2. 三档断点适配（1024/768/480）。
3. 关键操作按钮移动端可点击面积保证。

## 4. 技术方案建议（下一步）
1. 调度：接入 cron 或轻量任务调度器，按 3h 自动执行。
2. 存储：由文件升级到 SQLite（按 date upsert）提升可查询性。
3. 推送可靠性：加入重试、日志落盘与失败告警。
4. 观测：增加任务耗时、成功率、源可用性指标。

## 5. 运维建议
1. webhook 作为敏感配置，用环境变量管理。
2. key 泄露后立即重建机器人并废弃旧 key。
3. 周期性检查 RSS 源可用性并更新白名单。
